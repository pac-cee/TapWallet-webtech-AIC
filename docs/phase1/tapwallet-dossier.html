01

Abstract

TapWallet is a web-based digital wallet in which a customer holds a balance, tops it up, and pays a registered merchant; the merchant sees what it was paid; and an administrator manages both sides and oversees every movement of money. Rather than a single layer of forms over a database, the system is organised with Domain-Driven Design: the business rules live in a domain model of aggregates and value objects that knows nothing about Hibernate or JSF, the use cases sit in a thin application layer, and persistence and the web are pushed to the outside as replaceable detail.

The result is a system where a rule such as “a wallet may never go negative” is expressed once, inside the Wallet aggregate, and cannot be bypassed by any screen, service or query. Access control follows the same discipline: a signed-in user reaches only their own data, enforced by a server-side filter and by scoping every query to the session's user id.

02

Problem Statement

Small merchants in Rwanda largely rely on cash or USSD-based mobile money. Both carry friction a wallet model removes: cash needs change and manual counting; USSD needs the customer to dial a code, key in a PIN, and wait for an SMS the merchant must read off their own phone. Neither produces a machine-readable ledger, so reconciliation means re-reading SMS threads at the end of the day and a disputed payment has no single record both sides can point to.

There is a second problem, which is the one this phase takes seriously: in a system that moves money, correctness cannot depend on the screen being written carefully. If the rule that a balance may not go negative lives in a form handler, the next form that touches a balance can forget it. The architecture therefore has to make the rules impossible to skip, and has to keep each actor's data genuinely separate rather than merely hidden.

04

AS-IS Model

Today's point-of-sale flow for a small merchant:

  1. Customer and merchant agree a price at the counter.
  2. The customer pays cash, or dials a USSD code, selects “pay merchant”, enters the number and amount, and confirms with a PIN.
  3. The customer waits for a confirmation SMS.
  4. The merchant reads that SMS, or checks their own phone for an incoming-payment message.
  5. The sale is noted in a paper book, or not at all.
  6. At day's end the merchant reconciles by scrolling back through SMS messages one by one.

Every record is a message in someone's inbox. Nothing is queryable, and the two sides hold separate, unlinked evidence of the same sale.

05

TO-BE Model

The implemented flow, with one ledger both sides read from:

  1. The customer signs in and sees their wallet balance.
  2. They choose a registered merchant and an amount.
  3. The application service opens one Unit of Work and loads both aggregates.
  4. The domain service checks the rules: the payer is not the shop's own operator, the merchant is active, the wallet is active, the amount is positive and covered by the balance.
  5. The wallet is debited and the merchant credited through their own methods, and a Payment is recorded — all inside that single transaction, so the two balances can never drift apart.
  6. The customer sees the payment in their history; the merchant sees it, with the payer's name, in theirs; the administrator sees it in the platform-wide list and can reverse it, which moves the money back the same atomic way.

Because a wallet can only ever be a payer and a merchant only ever a payee, a customer paying another customer is not merely forbidden — it cannot be expressed in the model.

DDD Architecture

The code is split into four layers. Dependencies point inwards only: the domain depends on nothing, and the outer layers depend on the layer beneath. This is what lets the business rules be tested without a database and a web server.

Domain — the business, with no framework in it

Aggregates that own their invariants, value objects compared by value, repository interfaces, a domain service for the rule that spans two aggregates, and typed exceptions that name what went wrong.

domain/model/{user,wallet,merchant,payment,shared} · domain/repository · domain/service · domain/exception

Application — one class per actor's use cases

Orchestration only: load the aggregates, call their methods, save. Each method opens exactly one Unit of Work, which is the transaction boundary. No business rule lives here.

application/{Authentication,User,Merchant,Wallet,Payment}ApplicationService

Infrastructure — replaceable technical detail

Hibernate implementations of the domain's repository interfaces, the session factory, the transaction template, password hashing, the composition root, and the first-run seeder.

infrastructure/{persistence,security,config,bootstrap}

Presentation — JSF, and nothing else

Managed beans that read form fields and call an application service, a security filter, the custom validator, and a Facelets master template every page composes into.

presentation/{bean,filter,validator} · webapp/{admin,customer,merchant}

The clearest payoff is the Money value object. An amount and its currency travel together, arithmetic refuses to mix currencies, and rounding is decided in one place — so no screen can accidentally add francs to dollars, and no caller can hand a raw BigDecimal to a balance.

Roles & Security

RoleCan doCannot do
AdministratorFull CRUD on users and merchants; see every payment; reverse a payment; freeze accountsReach a customer or merchant screen
CustomerSee and top up their own wallet; pay any active merchant; read their own payment historySee another customer's wallet or payments; reach admin or merchant screens
MerchantSee their own shop, its revenue, and the payments it received with payer namesSee another shop's takings; pay from a wallet; reach admin screens

Access is enforced in two independent places, because hiding a link is not security:

  • At the door. SecurityFilter inspects every request. No session means a redirect to the sign-in page; the wrong role for a /admin/, /customer/ or /merchant/ path means a redirect to access-denied. Typing the URL by hand gains nothing.
  • In the query. Every customer- and merchant-facing read is keyed on the user id held in the session — findByPayerId(session user), findByMerchantOperatorId(session user) — never on an id taken from the request. Even a tampered form cannot address someone else's rows.

Passwords are stored as a salted SHA-256 digest behind the PasswordHasher strategy, and sign-in answers an unknown email and a wrong password with the identical message, so the form cannot be used to discover which accounts exist.

10

Software Qualities

Security

Salted password hashing, parameterised HQL throughout, server-side authorisation at the filter and again in every query, and identical messages for unknown-email and wrong-password.

Maintainability

Four layers with inward-only dependencies. Swapping Hibernate would touch one package; swapping the hashing algorithm touches one class.

Reliability

Every use case is one transaction, so a failed payment leaves both balances untouched — proven by a test that asserts exactly that after a rollback.

Testability

The domain has no framework dependencies, so its rules are tested as plain objects in milliseconds; the application layer is tested against a real H2 database.

Usability

One shared template, so every role sees the same layout with only its own menu; inline field errors; a sign-in page listing the demo accounts.

Scalability

Repository interfaces and a single composition root mean the storage engine, or an added bounded context, changes one layer rather than rippling through the screens.

56 automated tests pass: the domain rules as plain objects, and the application services against a real H2 database. Beyond the tests, the deployed application on Tomcat 9 was exercised over HTTP, and these were the observed results:

One defect was found and fixed during this work, and is recorded here because it illustrates why the domain is tested separately: the “you cannot pay your own shop” rule compared database ids, which are still null on an object that has not been saved, so the rule silently passed. User.isSameAs() now compares identity in a way that holds both before and after persistence.
