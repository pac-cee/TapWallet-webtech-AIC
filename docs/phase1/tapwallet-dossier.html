01

Abstract

TapWallet is a web-based digital wallet and contactless payment platform that lets a customer hold a balance, top up or withdraw funds, and pay a registered merchant by tapping an NFC-linked card or device. A merchant registers a business profile, accepts payments, and reviews revenue through a dashboard; an administrator oversees accounts and audits activity across the platform. The system does not reinvent Rwanda's payment rails — it demonstrates, in a contained web application, the pattern behind them: a wallet ledger, a tokenised card identifier standing in for an account rather than carrying a balance itself, and a validated, auditable transaction flow between two parties. This document proposes that full system and its data model, then implements a focused, working CRUD slice of it — the User and Wallet entities — using JSF 2.3, Hibernate 5, and an in-memory H2 database, with three layers of input validation and CSS applied in all three inclusion styles the assignment requires.

02

Problem Statement

Small merchants in Rwanda largely rely on cash or USSD-based mobile money for in-person payments. Both carry friction that a wallet-and-tap model is designed to remove: cash requires change and manual counting; USSD payment requires the customer to dial a code, key in a PIN, and wait for an SMS the merchant must read off their own phone to confirm the sale. Neither produces a machine-readable ledger the merchant can query later — reconciliation happens by re-reading SMS threads at the end of the day, and a disputed transaction has no single record both parties can point to. The underlying gap is not payment capability — MoMo and Airtel Money already move money — it is the absence, at the point of sale, of a shared, instantly-updated ledger that both the payer and the payee can see the moment a tap happens.

04

AS-IS Model

Today's point-of-sale flow for a small merchant, using cash or USSD mobile money:

  1. Customer and merchant agree a price at the counter.
  2. Customer either hands over cash, or dials the mobile money USSD code, selects “pay merchant”, enters the merchant's number and amount, and confirms with a PIN.
  3. Customer waits for a confirmation SMS from the mobile money provider.
  4. Customer shows the SMS to the merchant, or the merchant separately checks their own phone for an incoming-payment SMS.
  5. Merchant manually notes the sale (paper book, or nothing at all) — there is no shared, structured record either party can query later.
  6. At day's end, the merchant reconciles by scrolling back through SMS messages, one by one, against whatever cash or paper notes they kept.

Friction points: multi-step USSD entry, a confirmation the merchant must find and trust on sight, and reconciliation that depends on a human re-reading a message log.

05

TO-BE Model

The proposed tap-to-pay flow, with a single ledger both parties read from immediately:

  1. Customer taps their NFC card or device at the merchant's terminal.
  2. The terminal reads the card's token and sends it, with the sale amount, to the Payment API.
  3. The API resolves the token to a wallet, validates the customer and wallet are active, and checks the balance covers the amount.
  4. In one transaction, the API debits the customer's wallet and credits the merchant's wallet, then writes a transaction record.
  5. Both dashboards update immediately — the customer sees the debit, the merchant sees the credit — from the same record, with no SMS round-trip.
  6. An administrator can trace any transaction back to both wallets and both parties from the audit log at any time.

The NFC token identifies an account; it never carries a balance itself — the balance and the ledger live only on the backend, which is what makes the record trustworthy and disputable in the first place.

Software Qualities

Security

Salted SHA-256 password hashing, HQL with bound parameters (no string-built queries), and server-side validation as the source of truth — the client can be bypassed, the database cannot.

Usability

One reused form per entity for create and edit, inline field-level error messages, and the same two-link navigation (Home, the other list) on every page — nothing to get lost in.

Maintainability

A strict layering — entity, DAO, managed bean, view — with one class per responsibility, so a change to persistence never touches a view and vice versa.

Reliability

Every write runs inside a Hibernate transaction (open → act → commit → close); the DAO, bean, and validation layers are covered by 34 automated JUnit tests.

Performance

Primary-key lookups and an in-memory H2 database keep the demo instant; this is a teaching sandbox, not tuned for production load.

Scalability

Swapping H2 for a networked RDBMS is a one-line change to hibernate.cfg.xml; new entities (Merchant, Transaction, NfcCard) slot into the same DAO/bean pattern without touching User or Wallet.

09

Known Limitations

Deliberately kept simple for the assignment's scope (2 entities, full CRUD):

  • Wallet creation is a separate step. A wallet is opened through its own form, picking any existing user from a dropdown, instead of automatically alongside registration — so a user can exist without ever getting a wallet.
  • No money-movement demo. Without Merchant/Transaction implemented, there is nothing to pay yet — that is intentionally out of this submission's scope and left to the Phase-2/documented design above.
